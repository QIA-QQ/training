# 产品经理如何用 AI 从需求完善，到设计 Demo，到可开发的 PRD

## 一、现有产品经理工作范式 vs AI 辅助工作范式

过去，产品经理拿到一个需求后，通常会按照下面的流程推进：

```text
需求挖掘 / 需求分析
↓
写 PRD + 画原型
↓
需求评审
↓
推进开发
```

这种工作方式的问题在于，产品经理很容易过早进入“交付物制作”阶段：

```text
1. 花了很多时间写文档、画原型，但评审时发现方向不对，与业务方理解不一致，反复返工。
2. 复杂业务系统中，容易漏掉状态、权限、异常、存量数据等关键设计。
3. 产品经理大量时间被文档和原型消耗，真正用于需求判断和方案取舍的时间反而变少。
```

在 AI 辅助工作范式下，流程可以调整为：

```text
需求挖掘 / 需求分析（人 + AI 共同完成）
↓
输出可交互产品 Demo（AI 输出，人来评审和调整）
↓
需求评审（用 Demo 和关键规则讨论方案）
↓
输出 PRD（AI 整理，人来审核和补充）
↓
推进开发
```

这套工作范式的核心变化是：

```text
1. 从“先写文档”变成“先验证方案”。
2. 从“靠文字评审”变成“用 Demo 和规则评审”。
3. 从“产品经理独自补全所有细节”变成“AI 先补遗漏，人负责判断和取舍”。
```

实际落地时，可以按下面的链路推进：

```text
一句话需求
↓
用 AI 完善需求
↓
用 AI 生成产品 Demo
↓
用 Demo 进行方案评审
↓
用 AI 整理可开发 PRD
↓
推进开发
```

同时要区分两类场景：

```text
0-1 场景：从无到有设计一个新功能或新系统，重点是把问题、用户、场景、流程和 MVP 边界梳理出来。
1-100 场景：基于已有产品做新增、修改或优化，重点是先理解现有逻辑，再做增量变更。
```

## 二、如何用 AI 完善需求

### 要点总结

1. 单元化开发思维：需求功能过多时，拆分为多个功能开发单元。
2. 人定方向，AI 补遗漏：基础需求方向由人明确，AI 负责追问和补边界。
3. 1-100 先理解现状：先让 AI 复述现有系统逻辑，再做增量设计。

### 如何输入

输入范式：

```text
使用需求完善类 SKILL + 需求基础信息（问题、现状、目标、规则/约束、沟通纪要等）
```

#### 需求基础信息

【问题】
{谁遇到了什么问题？问题发生在什么场景？有什么影响？}

【现状】
{现在业务怎么处理？现有系统怎么支持？用户目前在哪一步卡住？}

【目标】
{这次希望改善什么？成功后用户/业务/系统会有什么变化？}

【规则/约束】
{已有业务规则是什么？哪些不能改？有哪些权限、状态、数据、合规或时间约束？}

【已有材料】
{会议纪要/截图/流程图/旧 PRD/接口文档/代码仓库路径/竞品参考}

#### 1-100 场景输入必做

1-100 的重点是“先理解现有产品，再做增量变更”。

```text
让AI理解现有产品逻辑的方式：
1. 让AI读取项目代码仓库
2. 提供产品页面截图+口喷产品逻辑

最好让AI复述产品逻辑的方式来对齐理解
```

### 输出标准

需求完善阶段的成功输出应达到“可以进入 Demo 的前置输入”：

- 背景与目标说清楚：为什么做、给谁用、解决什么问题。
- 用户与场景说清楚：有哪些角色，各自在什么场景下操作。
- 范围说清楚：本阶段包含什么、不包含什么、待确认什么。
- 主流程说清楚：用户从哪里进入，完成什么操作，系统如何反馈。
- 规则和边界说清楚：权限、状态、校验、异常、空状态、失败处理、历史数据。
- 页面设计说清楚：入口、布局、样式、交互。

## 三、如何用 AI 开发 Demo

### 要点总结

1. 明确Demo的演示要求：需不需要在线使用、需不需要后端交互、需不需要真实数据、需不需要权限校验等。
2. 先规格后开发：先确认开发规格说明书，再让 AI 写 Demo，避免反复修改。
3. 数据逻辑确认：哪些场景采用模拟数据，模拟数据如何构造，模拟数据如何展示

### 如何输入

使用Demo 生成类 skill + 补充Demo使用场景和数据逻辑

#### 通用输入范式

```text
请使用 Demo 生成 skill。
先基于需求方案输出文字版“开发规格说明书”，等我确认后再开始开发 Demo。

【Demo 目标】
{用于业务评审 / 方案评审 / 向开发说明交互 / 向领导展示 / 用户测试}

【需要演示的核心流程】
1. {流程 1}
2. {流程 2}
3. {流程 3}

【数据与接口】
- 使用模拟数据：{是/否}
- 需要真实接口：{接口名称或说明}
- 需要覆盖的数据状态：{正常/空/异常/权限不足/边界值}

【视觉与技术】
- 是否沿用现有系统风格：{是/否}
- 参考材料：{代码仓库路径/截图/设计稿}
- 输出形式：{单 HTML / React / Vue / 现有项目内开发}
- 是否需要响应式：{是/否，默认是}

【请你以开发视角输出】
开发目标、功能清单、页面结构、产品逻辑、数据与接口、视觉布局、交付形式、开发边界与验收点。
```

### 输出标准

Demo 阶段应分成两个层级验收。

第一层：开发前规格成功。

- 页面结构清楚到可以判断有哪些页面、区域、组件和入口。
- 产品逻辑写清楚主流程、状态流转、交互规则和异常/空状态。
- 数据与接口明确区分真实接口、模拟数据、待确认内容。
- 视觉与布局明确是否沿用现有系统，参考来源是什么。
- 开发边界写清楚本次做什么、暂不做什么、如何验收。

第二层：Demo 成品成功（可以打开、可以点击、主流程能走通、设计交互符合需求。）

## 四、如何用 AI 生成 PRD

### 要点总结

1. 复用完整上下文：在同一个需求梳理与Demo开发会话中生成PRD，共享项目完整上下文。
2. 区分 Demo 与正式需求：mock、占位、未接接口不等于产品需求。
3. 以html格式输出prd，将流程图可视化

### 如何输入

使用PRD 生成类 skill + 真实的调用及数据逻辑声明

#### 通用输入范式

```text
请使用 “PRD 生成 skill”，基于本次迭代版本的『需求方案』、『开发规格说明书』、『最终Demo』生成可开发 PRD。请遵循**剃刀原则**裁剪需求结构，不要机械套完整模板。

【本期真实开发范围】
包含：
1. {本期做什么}
2. {本期做什么}

不包含：
1. {真实产品本期不做什么}
2. {真实产品本期不做什么}

【特别注意】
在写 PRD 前，请先区分三类内容：

1. 正式需求：真实上线必须实现的产品逻辑、规则、接口、数据记录、权限、状态和验收项。
2. Demo 表达：Demo 中为了方便评审而呈现的页面布局、交互、文案和示例状态。
3. Demo 限制：Demo 中因演示目的产生的 mock、占位、不接接口、不持久化、不展示全部数据等限制。

只有“正式需求”进入 PRD 主体，对于Demo表达和限制类请向我确认。
```

### 输出标准

一份可开发 PRD 至少应满足以下标准：

- 需求主线清晰：为什么做、给谁用、解决什么、本期交付什么、不解决什么。
- 范围边界清晰：包含、不包含、待确认分开表达。
- 用户和场景清晰：角色、入口、使用场景、前后流程明确。
- 功能需求可执行：每个模块写清目标、入口、规则、状态、权限、验收。
- 流程和交互可落地：主流程、异常流、边界条件都有说明。
- 数据和规则可开发：字段、校验、状态流转、接口依赖、历史数据处理按需写清。
- 验收标准可判断：避免“提升体验”“优化效率”这种无法验收的表达。
