# Demo 开发规格生成

## 核心规则

不要直接开始开发。必须先把需求文档转化为一份简洁、可确认的开发规格说明书，并直接以文字形式展示在会话中。只有当用户明确确认规格无误，并表示可以开始开发后，才进入代码实现。

如果用户在同一条消息中已经说了“确认，可以开发”等类似授权，但必要澄清项仍缺失，也必须先补齐澄清项，再生成规格或开发。

## 工作流程

1. 阅读需求材料，识别本次 demo 的目标、页面、功能和边界。
2. 执行“开发前确认清单”。
3. 如果缺少必要答案或参考材料，只追问会阻塞规格生成或开发的问题。
4. 在会话中输出文字版“开发规格说明书”。
5. 请用户确认规格是否准确。
6. 用户明确确认后，按确认后的规格实现 demo。
7. 完成后验证页面或应用，尤其检查兼容式布局和主要交互。

## 开发前确认清单

在生成开发规格说明书前，必须确认以下事项；如果需求材料已经明确说明，可以直接引用并进入规格生成。

- 现有设计风格：询问新页面是否需要沿用现有系统的设计风格。
- 风格参考材料：如果需要沿用现有风格，检查用户是否已经提供项目代码仓库、已有前端代码、产品页面截图、设计稿或其他视觉参考。若没有，先追问用户补充。
- 数据与接口模式：询问 demo 是否需要真实调用后端接口并使用真实数据，还是使用虚拟数据。
- 接口与数据清单：基于需求文档，罗列可能涉及后端接口调用和页面数据展示的内容，让用户选择哪些接真实接口、哪些使用模拟数据，并允许用户补充需求中未提到的接口或数据。
- 输出格式：询问生成文件是否必须为 HTML。
- 单文件要求：如果需要 HTML，继续确认是否必须为单一内联文件，即 CSS 和 JavaScript 都写在同一个 HTML 文件中。
- 布局策略：默认采用兼容式响应布局，除非用户明确指定其他布局策略。

不要默认假设需要沿用现有风格、需要真实接口、或必须单一内联 HTML；这些选择会影响实现方式，必须确认。

## 开发规格说明书格式

规格说明书必须直接展示在会话中，不默认创建文件。内容要站在开发角度，具体、可执行、方便用户确认范围是否有误。

建议使用以下结构，并根据实际需求删减无关项：

```markdown
**开发规格说明书**

**一、开发目标**
- ...

**二、功能清单**
- ...

**三、页面结构**
- 页面/模块：
- 主要区域：
- 关键组件：
- 响应式规则：

**四、产品逻辑**
- 用户流程：
- 状态流转：
- 交互规则：
- 异常/空状态：

**五、数据与接口**
- 真实接口：
- 虚拟数据：
- 待用户补充/确认：

**六、视觉与布局**
- 是否沿用现有风格：
- 参考来源：
- 布局方式：

**七、交付形式**
- 技术形态：
- 文件形式：
- 是否单一内联文件：

**八、开发边界与验收点**
- 本次实现：
- 暂不实现：
- 验收标准：
```

规格末尾必须附上确认提示：

```text
请确认以上开发规格是否准确；确认后我再开始开发。
```

## 用户确认后的开发要求

用户确认后：

- 只实现已确认的范围。
- 如果提供了项目仓库，优先遵循仓库已有技术栈、目录结构、组件风格和代码规范。
- 如果生成 HTML，默认采用兼容式响应布局。
- 如果用户要求单一内联 HTML，将 CSS 和 JavaScript 内嵌到同一个 HTML 文件中；除非用户明确同意，不引入外部运行时依赖。
- 如果选择模拟数据，模拟数据要能完整展示目标流程、关键状态和边界情况。
- 如果选择真实接口，先阅读仓库或接口文档，再接入请求。
- 涉及数据加载时，应包含加载、空状态、错误状态和成功状态。
- 最终交付前检查桌面端和移动端宽度下的布局与主要交互。

## 追问方式

一次只问会阻塞下一步的最小问题集。罗列接口和数据时，使用便于用户选择的表达：

```markdown
我从需求中识别到这些可能涉及真实接口或数据展示的点，请确认哪些需要接真实接口，哪些可以使用模拟数据：
- 用户/权限信息：
- 列表数据：
- 详情数据：
- 新增/编辑/删除提交：
- 文件上传/下载：
- 统计指标：
- 通知/消息：
```

如果需求文档不够明确，可以在规格中给出合理推断，但必须标注为“待确认假设”。
