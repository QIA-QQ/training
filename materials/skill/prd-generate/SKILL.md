# prd-generate

## 目标

生成一份贴着需求本身展开的 PRD。文档必须服务于当前产品问题、当前阶段和当前交付目标，而不是套用固定大纲。

PRD 的逻辑来源优先级：

1. 用户明确表达的需求与约束
2. 头脑风暴阶段已确认的结论
3. Demo、截图、原型、竞品或已有文档中的可见信息
4. 基于产品常识的合理推断

对于第 4 类内容，必须标注为“建议”或“待确认”，不能写成用户已经确认的事实。

## 核心原则

- 贴需求输出：只写当前需求需要的章节。
- 以业务和用户目标驱动结构，而不是以模板驱动内容。
- 先界定范围，再写功能细节。
- 先写主流程，再补异常和边界。
- 明确可交付：让设计、开发、测试或业务方知道该做什么、不做什么、如何验收。
- 不因为 PRD 常见就强行加入无关章节，如商业模式、增长策略、埋点、风控、运营后台、多语言、会员体系等。
- PRD 写真实产品本期要交付的内容；Demo、原型或 mock 的限制不等于产品非本期范围，不应写入 PRD，除非用户明确要求输出 Demo 说明。
- 现有功能、页面、流程若本期不新增、不变更、不受影响，只能作为背景一句带过，不展开成章节、规则或验收项。

## 输入处理

### 1. 识别输入类型

根据材料判断本次 PRD 的来源：

- 头脑风暴结果：沿用已确认目标、范围、场景和待确认项。
- 一句话需求：先补充必要假设，再输出轻量 PRD，并标注待确认。
- Demo 或截图：从可见页面、组件、状态、交互入口和文案中抽取需求。
- 竞品参考：只提炼与用户目标相关的能力，不复刻无关模块。
- 已有文档：保留原始约束，修正结构和表达，不擅自改变业务含义。
- 代码或接口上下文：把已有实现能力转译成产品功能、规则和边界。

当输入来自 Demo、原型或截图时，必须先区分：

- 正式需求：真实上线必须实现的产品逻辑、规则、接口、数据记录或验收项。
- Demo 表达：Demo 中为了说明交互而可见的页面、状态、文案或布局。
- Demo 限制：Demo 中因演示目的而 mock、占位、不接接口、不展示或不实现的部分。

只有“正式需求”进入 PRD 主体。“Demo 限制”不写入 PRD 的非本期范围；非本期范围只用于真实产品本期也不做的内容。

### 2. 判断文档深度

按任务选择深度：

- 轻量 PRD：单功能、小页面、小工具、Demo 验证。
- 标准 PRD：有完整主流程、多个页面或多角色协作。
- 详细 PRD：涉及复杂权限、数据状态、异常流、接口联动、审核、交易、合规或跨系统。

不要在轻量需求里输出详细 PRD 的全部章节。

### 3. 处理信息缺口

如果缺口会影响核心方案，先问 1 个最关键问题。

如果缺口不影响当前文档成稿，可以继续输出，并在文档中标注：

- 待确认：需要用户或业务方确认。
- 建议默认：为了推进文档而提出的默认处理。
- 不在本阶段：暂不纳入范围。

## 结构裁剪

根据需求选择章节。下面是可选组件，不是固定模板。

### 必选章节

通常需要包含：

```markdown
# PRD 标题

## 1. 背景与目标

## 2. 范围

## 3. 用户与场景

## 4. 功能需求

## 5. 流程与交互

## 6. 验收标准

## 7. 待确认事项
```

### 按需加入的章节

仅在需求涉及相关内容时加入：

- 角色与权限：多角色、后台、审核、管理端。
- 页面结构：有明确页面、截图、Demo 或原型时。
- 数据字段：有表单、列表、详情、导入导出、接口或数据看板时。
- 状态机：涉及订单、审批、任务、发布、上下架、支付、退款等状态变化时。
- 异常与边界：涉及失败、撤回、超时、重复提交、权限不足、数据为空等情况时。
- 通知与消息：涉及站内信、邮件、短信、企业微信、推送时。
- 埋点与指标：用户明确要分析效果，或需求目标依赖数据衡量时。
- 非功能需求：性能、安全、兼容性、合规、可用性是实际约束时。
- 版本规划：需求较大，需要分期交付时。

### 应避免的章节

如果输入没有涉及，不要强行加入：

- 市场分析
- 商业模式
- 竞品矩阵
- 组织架构
- 运营策略
- 增长策略
- 财务测算
- 完整技术方案
- 与当前功能无关的后台系统

## 写作流程

### 1. 提炼需求主线

用 3-5 句话先说明：

- 为什么要做
- 给谁用
- 解决什么问题
- 本阶段交付什么
- 不解决什么

### 2. 定义范围

用“包含 / 不包含 / 待确认”写清边界。

范围比功能列表更重要。范围不清时，功能越写越散。

定义范围时按下面口径裁剪：

- 包含：本期真实开发需要新增、变更或验证的内容。
- 不包含：真实产品本期明确不做的内容。
- 不写：仅用于 Demo 演示的 mock、占位、未接真实接口、未展示埋点等限制；以及本期不涉及改动的既有页面和流程。
- 背景一句带过：理解本需求必须知道、但本期不改的既有能力。

### 3. 写主流程

先写用户完成目标的主路径。例如：

```markdown
1. 用户进入页面
2. 系统展示当前状态与可操作入口
3. 用户填写或选择信息
4. 系统校验并提交
5. 系统返回结果，并提供后续操作
```

再补充异常流和边界条件。

### 4. 写功能需求

每个功能模块建议包含：

- 目标：这个模块解决什么问题。
- 入口：用户从哪里进入。
- 规则：系统如何展示、校验、保存、流转。
- 状态：空状态、加载中、失败、成功、禁用、只读等。
- 权限：谁能看、谁能操作。
- 验收：如何判断做对了。

没有涉及的维度可以省略，不要硬填。

### 5. 写验收标准

验收标准要可判断，避免空泛表达。推荐使用：

```markdown
- 当 [前置条件] 时，用户可以 [操作]，系统应 [结果]。
- 当 [异常条件] 时，系统应 [反馈/限制/兜底]。
```

### 6. 自检并裁剪

输出前检查：

- 是否每一章都能追溯到用户需求、头脑风暴结论、截图/Demo 或明确推断。
- 是否有与当前需求无关的模板章节。
- 是否把不确定内容写成确定事实。
- 是否遗漏主流程、边界、验收标准。
- 是否存在“体验优化”“提高效率”等不可验收表述。

发现冗余章节时删除；发现缺口时标注待确认。

## 推荐输出格式

根据需求深度选择结构。

### 轻量 PRD

```markdown
# [功能/页面名称] PRD

## 1. 背景与目标

## 2. 范围

### 2.1 本次包含

### 2.2 本次不包含

## 3. 用户与场景

## 4. 核心流程

## 5. 功能需求

## 6. 验收标准

## 7. 待确认事项
```

### 标准 PRD

```markdown
# [产品/功能名称] PRD

## 1. 背景与目标

## 2. 需求范围

## 3. 用户角色与使用场景

## 4. 业务流程

## 5. 页面/模块结构

## 6. 功能需求

## 7. 数据与规则

## 8. 异常与边界

## 9. 验收标准

## 10. 待确认事项
```

### 详细 PRD

在标准 PRD 基础上，按需增加：

```markdown
## 权限矩阵

## 状态流转

## 字段说明

## 通知规则

## 埋点与指标

## 非功能需求

## 版本规划
```

## 输出要求

- 使用中文输出，标题或专有名词可以保留英文。
- 文档结构必须按输入裁剪，不能机械套用完整模板。
- 所有功能点都应能对应到需求来源或明确推断。
- 不确定内容必须标注，不要伪装成已确认需求。
- 面向开发和测试可执行，少写口号，多写规则、流程和验收。
- 当正式 PRD 涉及流程图、状态图、时序图、架构图、图表、字段表、权限矩阵、验收用例表等需要可视化阅读的内容时，应同时交付 Markdown 源文件和 HTML 可视化文件。Markdown 文件作为可维护源文档，HTML 文件作为面向开发、测试和评审的阅读版本；HTML 中应将 Mermaid 图、表格和目录等内容渲染为可直接查看的可视化形态。
- 仅当整份 PRD 都是文字说明，且不包含流程图、图表、表格、矩阵或其他可视化内容时，可以只在对话中输出或只交付 Markdown 文档。
- 需要生成文件时，优先按用户指定位置保存；用户未指定位置时，将 Markdown 源文件和 HTML 可视化文件保存到当前工作区合适的输出目录，并在回复中给出文件路径。
